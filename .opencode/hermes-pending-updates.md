- **Trigger:** Gregory reported 2026-08-01i's fix was insufficient — the two `HorizontalScrollShowcase` rows still didn't lock the viewport and scroll horizontally to completion as intended (lock at the section, drive through all items horizontally via vertical scroll, then release to continue down the page).

That reproduced the bug directly: scrolling "Work you can explore" down in fine (40px) steps showed the row jump from `transform: translateX(0)` straight to the fully-scrolled `translateX(-433px)` end state in a single step, with `position` never observed as `fixed` — i.e. no visible lock, the horizontal pass never played, it just snapped to "done."
- **Root cause:** every `HorizontalScrollShowcase` instance calls the *global* `ScrollTrigger.refresh()` (via a `ResizeObserver` on its panels, whose callback fires once immediately on `.observe()`, by spec) shortly after it lazily mounts (each instance mounts independently, gated by its own 600px-proximity `useInViewport`). `ScrollTrigger.refresh()` recalculates every trigger's `start`/`end` from the *live* DOM — including whichever pin is *currently engaged* (`position: fixed`). (2026-08-01i's fix — decoupling the outer `.reveal-item` fade cascade from the pin — was a real, independent correctness issue and stays in place, but it wasn't the cause of the lock/scrub failure itself.)
- **Fix:** `src/components/ui/HorizontalScrollShowcase.tsx` — (1) skip the `ResizeObserver`'s mandatory initial callback (the trigger was just created against current, already-correct layout, so that first refresh was pure redundancy and the main source of collisions), and (2) guard all subsequent refreshes: before calling `scrollTriggerPlugin.refresh()`, check `scrollTriggerPlugin.getAll().some(st => st.isActive && st.vars.pin)` and, if any pin is currently active anywhere on the page, defer and retry every 200ms until nothing is pinned.

### 2026-08-01g addendum 2 — Single-pass sweep: fixed visible loop reset

### 2026-08-01 addendum — Fixed three real HorizontalScrollShowcase bugs Gregory caught

- **Feedback (Gregory, verbatim):** "the horizontal scrolling areas need some work as currently the scroll continue while their animation plays instead of having the view lock, animations that are supposed to play when scrolling back upwards do not play correctly. the animated SVG items so not work and are broken, not able to be viewed as well in the side scroll section for the services."
- Got a temporary Playwright (`playwright@1.62.1`, `--no-save`, removed after — `package.json`/`package-lock.json` confirmed untouched) working against the running dev server to reproduce and verify all three, since the environment has no persistent browser tool.
- **Bug 1 — SVG stories broken/invisible in the services showcase:** `Home.tsx` never imported `ServicePages.css`, so `ServiceFamilyVisual`'s absolutely-positioned story markup (`.service-story`, `.atelier-story`, `.seo-review-story`, `.story-connector`, etc.) had zero layout rules on the homepage — confirmed via grep showing every other page that renders these components imports that stylesheet except `Home.tsx`. Fixed by adding the import. Also added a `.horizontal-scroll-showcase-panel .service-story` sizing rule to `ServicePages.css` (mirrors the existing `.service-family > .service-story` rule) since the Home embedding context (`.card` wrapper) never matched the selector that gives the story its width/min-height/background — without it the story would still collapse to 0 height even with the CSS loaded. Verified via Playwright: story panels now measure real dimensions and render the full crawl → pages → priorities → review/scoped-implementation sequence, confirmed by screenshotting the same panel across several seconds of its loop.
- **Bug 2 — pin releases before the horizontal animation finishes ("scroll continues while animation plays"), and the same desync on scroll-up:** root cause was `scrub: 0.6` on the pinned tween in `HorizontalScrollShowcase.tsx`. A numeric scrub value intentionally smooths the tween with a catch-up delay behind the raw scroll position; combined with `pin: true`, the pin unlocks at the scroll position matching progress 1.0 while the eased tween is still lagging toward its target, so the section un-pins with the horizontal reveal still visibly catching up — and the same lag shows up in reverse on scroll-up. Verified with Playwright by sampling the trigger's `position` (`static`→`fixed`→`static`) and the track's transform at 250px scroll increments: before the fix, `position` returned to `static` while `transform` was still short of its final value (e.g. `-445px` of `-512px`); after switching to `scrub: true` (tight 1:1 tracking, no smoothing), the transform reaches its exact target in the same frame the pin releases, in both scroll directions.
- **Bug 3 (defensive, not directly reported but same component) — stale scroll-distance measurement:** `scrollDistance` was captured once as a plain number when the effect ran, so if panel content (images, late-loading story CSS) changed size afterward, the pin's `end` distance and the tween's `x` target silently went stale even on `ScrollTrigger.refresh()`, since `refresh()` only re-evaluates values that are functions. Converted both to function-based getters (`getScrollDistance()`) so `invalidateOnRefresh` actually recomputes them, and added a `ResizeObserver` on the panels track that calls `scrollTriggerPlugin.refresh()` when content size changes, cleaned up via matchMedia's own context-revert return-function.
